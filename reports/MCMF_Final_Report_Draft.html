Abstract

This report studies interceptor assignment in a mobile wireless sensor network (WSN) used for cooperative multi-target tracking. In the original simulation, conflict resolution was based on a legacy minmax objective that attempts to minimize the worst team cost among the requesting targets. This objective protects the weakest target assignment, but it does not directly optimize the total resource burden imposed on the sensor network. The proposed Version 46 (V46) assignment module reformulates the problem as a min-cost max-flow (MCMF) problem. Its objective is defined in two steps: first maximize the number of requested interceptor positions filled, then minimize the total assignment cost among solutions with the same number of filled positions.

The report compares MCMF and the legacy minmax method using the same simulation candidates and the same cost matrices. A real simulation event at t = 39.50 s is used as the primary worked example. The results show that MCMF fills all requested interceptor positions and reduces the total assignment cost from 1.182 to 1.085 in this event. The report also discusses limitations: total-cost minimization does not explicitly protect the worst target team, MATLAB workstation timing is only a prototype baseline, embedded deployment must include communication latency, and the current coordination model is temporary leader-based rather than fully decentralized consensus.

1. Introduction

Mobile wireless sensor networks are useful for cooperative multi-target tracking because mobile sensors can reposition themselves as targets move through the sensing field. In this project, the WSN tracks up to three moving targets, and each target is intended to maintain two active trackers to preserve tracking continuity during handover.

The central problem addressed in this report is interceptor assignment during proactive handover. When an active tracker predicts that it will lose a target, idle or non-tracking sensors are dispatched toward a predicted interception point before the target is lost. This process becomes difficult when multiple targets request interceptor assignments at the same time, or when a later target attempts to select a sensor that is already executing an interception task for another target. In these cases, independent target-by-target bidding can create conflicts, duplicate assignments, or unnecessary reassignments of sensors. Moreover, due to limited sensor availability and feasibility constraints, some targets may receive fewer than the desired maximum number of interceptors.

The original conflict-resolution method used a minmax-style objective. For simultaneous interceptor-assignment conflicts, the minmax method attempted to select teams such that the worst target team cost was minimized. This is a fairness-oriented objective: no target should receive a very poor team if a more balanced solution is available. In V46, the interceptor assignment problem is formulated as a global optimization problem and solved using a min-cost max-flow framework. The method first maximizes the number of requested interceptor positions filled across all competing targets and subsequently minimizes the total assignment cost. This replaces the fairness-oriented minmax objective with a joint assignment objective defined over all competing targets.

In the resulting V46 logic, an existing interceptor assignment is not protected by simple first-come-first-served priority. If a later target requests a sensor that is already intercepting for another target, the affected targets are pulled into one joint reselection event and the final assignment is reoptimized over the full affected set.

The main contributions of this report are:

  • It reformulates interceptor selection as a global assignment problem between candidate sensors and target interceptor assignments.
  • It compares MCMF and minmax assignment using the same candidate sensors and cost matrices.
  • It uses natural simulation evidence to show how the two objectives can lead to different decisions.
  • It analyzes feasibility and communication limitations for Crazyflie 2.0 deployment.

2. Literature Review

2.1 Cooperative Tracking in Mobile WSNs

Wireless sensor networks were originally studied as networks of small sensing, computation, and communication devices with limited resources. Akyildiz et al. describe WSNs as systems constrained by energy, processing, and communication capacity, which is directly relevant to this project because interceptor selection consumes sensor motion, communication, and computation resources [1]. Mobile sensor network surveys further emphasize that mobile sensors can support target searching and tracking, but that mobility introduces planning, coordination, and estimation challenges [2].

The multi-target tracking aspect of this project is related to cooperative multi-robot observation. Parker's CMOMMT work frames the problem as maximizing the time during which moving targets are observed by a team of robots with limited sensing range [3]. Kolling and Carpin also study cooperative observation of multiple moving targets using distributed coordination, prediction of target loss, and local assignment mechanisms [4]. These works motivate the use of mobile sensors and cooperative handover. However, this project focuses more narrowly on the assignment step that occurs when multiple targets compete for replacement interceptors.

2.2 EKF-Based Tracking and Prediction

The simulation uses an Extended Kalman Filter (EKF) to estimate each target state as [x, y, vx, vy]. EKF-based methods are widely used when tracking moving targets with noisy measurements and nonlinear observation models. Bar-Shalom, Li, and Kirubarajan provide a standard tracking and navigation reference for state estimation under uncertainty [5]. More recent WSN tracking work continues to use EKF variants to improve localization and tracking accuracy in sensor networks [6].

In this project, EKF estimates are not the final contribution by themselves. Instead, they provide the prediction inputs for handover: estimated target position, velocity, predicted loss time, and predicted interception point. This makes the assignment problem dependent on estimation quality. A sensor is not only bidding based on geometric distance; it is bidding on an intercept point whose reliability depends on tracking convergence and prediction stability.

2.3 Auction and Bidding-Based Task Allocation

Multi-robot task allocation (MRTA) provides the assignment framework for this project. Gerkey and Mataric show that many multi-robot coordination problems can be analyzed as optimization problems, including assignment and scheduling problems [7]. Market-based or auction-based methods are common because each robot or sensor can express its suitability for a task as a scalar utility or cost. Bertsekas' auction algorithms also connect bidding ideas to assignment and network flow problems [8].

The current simulation already contains a bid cost that combines distance from home, distance to the intercept point, arrival timing, and estimate uncertainty. Therefore, MCMF does not replace the bidding idea. It uses the existing bid as an assignment cost and changes how competing bids are resolved when several targets need interceptors at the same time.

2.4 Minmax and Min-Cost Assignment Objectives

The legacy minmax method and the proposed MCMF method answer different questions. Minmax asks: which assignment minimizes the worst team cost among targets? This protects the least-favored target team and is appropriate when fairness or worst-target quality is the dominant objective. Min-cost assignment asks: which feasible assignment produces the lowest total cost? In this project, MCMF further adds a first priority: fill as many requested interceptor positions as possible before minimizing cost.

Minimum-cost flow is a standard network optimization model for assigning limited resources to demand nodes while respecting capacity constraints. Ahuja, Magnanti, and Orlin present minimum-cost flow as a core network optimization problem with broad applications, including assignment and matching [9]. This makes MCMF suitable for the interceptor problem because each sensor can be assigned at most once, each target has a limited number of required slots, and each sensor-target pairing has a cost.

2.5 Distributed Coordination and Embedded Constraints

A real WSN cannot be evaluated only by optimization quality. It must also consider communication latency, coordinator failure, and embedded processor limitations. Decentralized auction methods, such as the consensus-based auction and bundle algorithms, show one way to resolve assignments without a permanent central controller by combining bidding with local consensus [10]. These methods are relevant because the current simulation still uses an event-local coordinator to collect bids and run the global assignment.

Crazyflie-class hardware provides a useful embedded reference point. The Crazyflie 2.0 uses an STM32F405 main processor at 168 MHz and an nRF51822 radio/power processor at 32 MHz [11]. The STM32F405 includes a single-precision floating point unit, but it is still very different from a workstation CPU running MATLAB [12]. The Crazyflie radio stack also imposes packet-size, polling, retry, and peer-to-peer communication constraints [13], [14]. These constraints mean that a final deployment claim requires C-level timing and communication-aware validation, not only MATLAB runtime measurement.

3. System Model and Problem Formulation

3.1 System Model and Assumptions

This section models the interceptor assignment problem at an abstract level rather than at the level of a specific simulation instance. Consider a wireless sensor network with N mobile sensors that cooperatively track up to K targets. During a handover event, each requesting target may require up to L interceptor positions. The model is restricted to a planar workspace, so all positions are represented in R^2.

Each sensor i has a home position h_i in R^2 and a current position s_i(t) in R^2. Each target k has state x_k(t) = [p_k(t), v_k(t)], where p_k(t) is target position and v_k(t) is target velocity. Sensors are assumed to share the same sensing and mobility limits, characterized abstractly by detection radius r_d, communication range r_c, and sensor speed v_s. If topology-preservation language is retained, each sensor may also be constrained by a maximum allowed displacement from home, denoted d_max.

Target detection occurs when ||s_i(t) - p_k(t)|| <= r_d. Upon detection, sensor i obtains a noisy position measurement of target k,

z_{i,k}(t) = p_k(t) + n(t)

where n(t) is zero-mean measurement noise with covariance R. Throughout the report, calling targets are targets that have reached PENDING_SELECTION and are requesting new interceptors. Candidate sensors are all non-active-tracker sensors eligible to bid for those targets; this set may include idle sensors, returning sensors, or sensors already intercepting for another target. Active trackers are the sensors currently assigned to track a target and are excluded from interceptor bidding. A predicted interception point is the point to which a selected interceptor is dispatched, and an interceptor assignment is the event-level pairing between a candidate sensor and a requesting target.

The system assumptions used in the remainder of the report are as follows: the workspace is planar; sensors are homogeneous; assignment is event-triggered when a target reaches PENDING_SELECTION; and active trackers are excluded from candidate bidding during the current event.

A further event-level assumption is important for the later MCMF formulation. If a provisional selection reuses a sensor that is already assigned as an interceptor for a different target, the previous owner target is added to the same decision event. The assignment problem is therefore solved over the closed set of mutually affected targets, not only over the newest requesting target.

3.2 Problem Formulation and Bidding Cost

When one or more targets enter PENDING_SELECTION, the system defines a set of calling targets and a set of candidate sensors. For each calling target, the system computes a predicted intercept point. For each candidate sensor and each calling target, the system computes one bid cost. These bid values form the assignment cost matrix:

B[i, j] = bid cost of assigning candidate sensor i to calling target j

This matrix is the pre-expansion view of the problem. In the MCMF construction of Section 4, each target column is duplicated into L target-slot nodes so that every requested interceptor position is represented explicitly.

Each calling target requires L interceptor positions. The bid cost represents how suitable a sensor is for a target. A lower bid indicates a better candidate. The weighted bid model used in this report is:

bid = w1 * P_home + w2 * P_spatial + w3 * P_temporal + w4 * P_uncertainty

The four terms have system meaning:

  • P_home penalizes displacement from the sensor's home grid position.
  • P_spatial penalizes distance from the sensor to the target intercept point.
  • P_temporal penalizes poor arrival timing relative to the target motion and loss deadline.
  • P_uncertainty penalizes low confidence in the shared target estimate.

Therefore, total bid cost is not an arbitrary number. It is an approximation of network-wide resource burden, including sensor displacement, intercept feasibility, timing quality, and estimation reliability.

The interceptor assignment problem can be stated as follows. Given a set of calling targets, a set of candidate sensors, and a sensor-target cost matrix, assign candidate sensors to requested interceptor positions such that:

  • Each requesting target needs L interceptor positions.
  • Each candidate sensor can be assigned at most once.
  • Active trackers are excluded from the candidate set.
  • If a provisionally selected sensor is already assigned as an interceptor for another target, that target must be included in the same joint assignment event.
  • The assignment should fill as many requested interceptor positions as possible.
  • Among assignments with the same number of filled positions, the assignment should minimize total bid cost.

Conflicts occur when multiple targets compete for overlapping low-cost candidates, or when a later target attempts to select a sensor that is already assigned as an interceptor for another target.

These rules mean that existing interceptor assignments are provisional rather than frozen. An already-dispatched interceptor may be retained or reallocated, but only through a joint feasible reassignment that simultaneously updates every affected target.

4. Proposed MCMF-Based Assignment Method

4.1 Assignment Workflow

Operationally, the MCMF-based procedure begins when a target enters PENDING_SELECTION. The system constructs the event-local candidate set, predicts interception points for the calling targets, and evaluates one bid for each candidate sensor and each calling target. If a new selection would reuse a sensor already assigned to another target, the affected targets are grouped into a joint reselection event. The shared assignment is then solved once, and the selected interceptors are written back into the sensor-level FSM states.

Internally, the MCMF solver expands each calling target into L requested interceptor positions and builds a directed flow graph:

  • The source connects to each candidate sensor node with capacity 1 and cost 0.
  • Each candidate sensor connects to each target position with capacity 1 and cost equal to the corresponding bid value.
  • Each target position connects to the sink with capacity 1 and cost 0.

The capacity from the source to each sensor enforces the rule that one sensor cannot be assigned to more than one target. The target-position-to-sink capacity enforces the number of requested interceptors per target. The cost on each sensor-to-target-position edge encodes the bid cost for assigning that sensor to that target.

Table 1. Flow-graph interpretation of the joint assignment problem.
Graph Element Meaning in the WSN assignment event
One sensor node One non-active-tracker candidate sensor that can serve at most one interceptor slot in the current event.
One target-slot node One requested interceptor position for one calling target after slot expansion.
One sensor-to-slot edge A feasible assignment with cost equal to the bid value for that sensor-target pairing.
Unit capacities They enforce one use per sensor and one sensor per requested target slot.

An important design choice is that the event-local candidate set contains all non-active-trackers, not only idle sensors. As a result, a sensor already in INTERCEPTING state can appear in the new event. If a provisional assignment wants to reuse that sensor, the previously served target is pulled into the joint reselection set and the combined problem is solved again. The MCMF stage therefore decides whether the previous interceptor owner should keep the sensor or release it as part of the best global reassignment.

4.2 Objective

The MCMF solver uses a lexicographic two-step objective. The first objective is to maximize the number of requested interceptor positions filled across all competing targets. The second objective is to minimize the total assignment cost among solutions with the same number of filled positions. In implementation, this lexicographic rule is converted into a single min-cost flow by modifying each feasible sensor-to-target-slot edge cost as follows:

c'_{i,j,l} = c_{i,j} - M, with M > any achievable positive total bid difference in the event

Here c_{i,j} is the original bid cost for assigning sensor i to target j, and l indexes the duplicated interceptor slots of that target. Because each additional filled slot reduces the objective by M, the optimizer always prefers filling one more requested position before optimizing the remaining cost terms. This is the same assignment-reward construction used in the MATLAB implementation.

Objective 1: maximize requested interceptor positions filled
Objective 2: minimize total assignment cost, conditional on Objective 1

4.3 Why This Objective Fits the System

The main system requirement is to sustain target tracking by replacing trackers before they lose contact. Therefore, filling as many requested interceptor positions as possible is a feasibility objective. If a target does not receive enough replacement sensors, then the system may lose tracking continuity regardless of how fair the remaining assignment appears. This is why the proposed method first maximizes the number of requested interceptor positions filled.

After the position-filling objective is handled, total cost becomes the correct secondary objective for this system because the bid cost already represents network-wide resource burden. A solution with lower total bid cost tends to use sensors that are closer to home, closer to the intercept point, better timed, and supported by more reliable estimates. Over repeated handovers, reducing this total burden helps preserve future network availability.

The legacy minmax objective remains meaningful. It protects the worst target team and is appropriate when worst-target fairness is the dominant mission goal. However, minmax may accept higher total resource expenditure to balance team costs. In a resource-constrained mobile WSN, it is not always desirable to sacrifice total network efficiency only to improve the worst single team cost, especially when the dual-tracker requirement and handover gates already provide target-level protection before assignment.

4.4 Limitation of the Objective

The proposed MCMF objective does not explicitly minimize the worst target team cost. Therefore, it does not provide the same fairness guarantee as minmax. If a mission requires strict worst-target protection, the assignment formulation should be extended with a maximum per-target team cost constraint or with a secondary fairness term. If the mission also requires assignment stickiness, then reassignment penalties or hard lock constraints should be added for already-dispatched interceptors. In this report, minmax is treated as a valid fairness baseline, not as an incorrect method.

4.5 Decentralized Coordination Protocol and Failure Handling

The decentralization question for the current MCMF design must be answered at the event level. The current simulation is best interpreted as leader-coordinated, event-local assignment rather than fully decentralized consensus.

  • For a single-target handover, the PRIMARY_TRACKER of the calling target acts as the event leader.
  • For a joint conflict or reselection event, the PRIMARY_TRACKER of the target with the earliest predicted loss time acts as the event leader.
  • If there is a tie, the lower target ID and then the lower sensor ID are used as tie-breakers.

The event leader broadcasts the request for bids and temporarily aggregates only the information needed for the current event: the event ID, the IDs of the calling targets, the predicted intercept points or deadlines, and one bid vector from each candidate sensor. This produces an event-local communication count of:

N_messages = 1 request + M bid messages + 1 result + A acknowledgments

where M is the number of candidate sensors and A is the number of acknowledgments, typically up to the number of assigned interceptors.

If no assignment result is broadcast before a timeout, the SECONDARY_TRACKER of the same target becomes the backup leader. If the backup leader also fails, the system falls back to a local greedy reassignment for that event or retains the currently valid interceptors until the next event window. Any stale event bids are discarded after timeout.

This protocol removes a permanent central controller, but it still requires one sensor to keep bids temporarily for the current event. Therefore, it does not satisfy a strict no-bid-storage decentralized requirement. The honest conclusion is that the current design is leader-coordinated and event-local, not fully decentralized in the professor's strict sense. A truly decentralized version would require a distributed auction or consensus-based assignment method instead of event-local MCMF aggregation.

5. Simulation Results and Feasibility Analysis

5.1 Simulation Setup and Comparison Protocol

The final report uses one natural simulation conflict as the main evidence instead of organizing the narrative around multiple staged validation cases. The reported comparison is based on a natural joint reselection event observed in a full V46 simulation run. In this instantiated simulation, the WSN uses N = 25 sensors arranged in a 5 x 5 staggered hexagonal grid and tracks up to K = 3 targets. Each requesting target may receive up to L = 2 interceptor positions during a handover event. The simulation time step is dt = 0.1 s.

The simulation geometry and motion parameters are fixed as follows: node spacing is 12 spatial units, sensor detection radius is 1.5 units, communication range is 18 units, and sensor speed is 0.75 units/s. The estimation and assignment parameters are also fixed: the EKF process noise covariance is Q = 0.01 I, the measurement noise covariance is R = 0.0025 I, and the bid-weight vector is (w1, w2, w3, w4) = (0.4, 0.3, 0.2, 0.1). The final comparison uses the same natural event, the same candidate sensors, and the same bid-cost matrix for both methods; the only changed element is the assignment objective. Solver correctness was checked separately before this final comparison, but those earlier checks are not the main evidence in the report.

5.2 Natural Simulation Comparative Result

The main real-run evidence comes from a full V46 simulation log. At t = 38.90 s, target 1 had already selected sensors 10 and 14 as interceptors. At t = 39.50 s, target 2 entered PENDING_SELECTION. A provisional selection for target 2 attempted to use sensor 14, but sensor 14 was already assigned as an interceptor for target 1. Therefore, target 1 was added to a joint reselection group, its intercept point was refreshed using tracker 9, and the system solved a shared assignment problem for targets 2 and 1.

This event also clarifies the reassignment policy. In V45, sensor 14 remained eligible for target 2 because the candidate filter excluded only active trackers; once target 2 selected sensor 14, target 1 simply lost that interceptor without a compensating joint reoptimization. V46 changes this semantics. Sensor 14 is still eligible in the candidate pool, but its reuse now triggers joint reselection rather than unilateral takeover.

Therefore, V46 does not hard-lock an existing interceptor to its previous target. Instead, it temporarily treats the current interceptor ownership as provisional, refreshes the affected targets' intercept data, and solves a combined assignment problem. The joint optimizer may keep sensor 14 with target 1 or may reassign it to target 2 if that produces a lower global objective while still reassigning target 1 consistently in the same event.

Worked Example: Why the Methods Differ

Step 1: Conflict trigger.

Target 2 entered PENDING_SELECTION and sensor 14 appeared as its best candidate. However, sensor 14 was already assigned to target 1. Allowing target 2 to take sensor 14 would disrupt target 1's existing interception task. Therefore, the system grouped target 2 and target 1 into a joint reselection problem.

Step 2: Legacy minmax decision.

The legacy method evaluates non-overlapping two-sensor teams and selects the combination that minimizes the maximum team cost across targets. In this event, it assigns target 2 to sensors 20 and 13 with team cost 0.591, and target 1 to sensors 14 and 18 with team cost 0.590. The result is very balanced because the two team costs are almost equal.

Step 3: MCMF decision.

MCMF first fills all four requested interceptor positions. It then minimizes total cost over the joint reassignment problem, which means sensor 14 is allowed either to remain with target 1 or to move to target 2 if the combined objective improves. In this event, the optimal solution keeps sensor 14 with target 1 and assigns target 2 to sensors 13 and 20. The resulting team costs are 0.591 for target 2 and 0.493 for target 1, for a total cost of 1.085 compared with 1.182 for legacy minmax.

Step 4: System interpretation.

The legacy solution is fairness-oriented: it gives both targets nearly equal team costs. The MCMF solution is system-efficiency-oriented: it keeps all requested positions filled and reduces the total network burden. In this event, MCMF does not worsen the worst team cost, but it does avoid an unnecessarily expensive assignment for target 1. This supports the argument that total-cost minimization is useful when the system objective is to preserve global WSN resources across repeated handovers.

5.3 Crazyflie-Class Feasibility Analysis

Crazyflie 2.0 is a useful lower-end reference platform for this project. Its main application processor is an STM32F405, an Arm Cortex-M4 processor at 168 MHz with 192 KB SRAM and 1 MB flash [11]. ST's documentation states that the STM32F405 family includes a single-precision floating point unit and DSP instructions [12]. Therefore, Crazyflie 2.0 is not a no-FPU platform, but it is still much less capable than a 4.5 GHz workstation CPU.

On the workstation, MCMF-only computation is approximately 1.254% of a 0.1 s time step. However, this is not a deployment guarantee. It is a MATLAB prototype timing result on a workstation CPU.

The measured MATLAB runtime should be treated as an optimistic prototype baseline. A laptop CPU running MATLAB has a different architecture from a small embedded processor. It has different cache behavior, memory bandwidth, instruction scheduling, and floating point support. A deployed implementation would run in C or C-like firmware, not MATLAB. It may use single-precision floating point, fixed point, or soft-float arithmetic depending on the target platform.

Using the measured MCMF-only workstation time of 0.001254 s and a simple frequency-scaling estimate from 4.5 GHz to 168 MHz gives:

estimated_cycles = 0.001254 * 4.5e9 = 5.64e6 cycles
estimated_time_at_168MHz = 5.64e6 / 168e6 = 0.0336 s

This is approximately 33.6% of a 0.1 s time step for computation alone. Because this estimate ignores communication, firmware scheduling, sensor processing, and flight control load, it should be treated as a warning rather than a guarantee.

T_total = T_request + T_bid_collection + T_compute + T_result + T_ack + T_retry

The 0.1 s reaction window cannot be assigned entirely to computation. Communication, retries, and control overhead must also be included. For one event, the communication load is:

N_messages = 1 request + M bid messages + 1 result + A acknowledgments

For the natural t = 39.50 s event, M = 23 candidate sensors, so even before retries the event requires one request broadcast, 23 bid messages, one result broadcast, and optional acknowledgments from the selected interceptors. If the system assumes an optimistic 2 ms per reliable packet transaction based on Bitcraze's low-latency Crazyradio discussion for 2 Mbps communication without retries, then the event-level communication budget can consume tens of milliseconds before medium access and control overhead are included [13].

The correct statement is therefore cautious: Crazyflie-class execution may be computationally plausible for event-triggered assignment, but a hard 0.1 s end-to-end guarantee is not yet proven. The current design must still absorb event communication, timeout handling, and control scheduling in addition to assignment computation.

5.4 Embedded Validation Plan

Because the report does not yet include true Crazyflie timing measurements, the next step should be a processor-level validation rather than an unsupported deployment claim. The recommended embedded validation procedure is:

  • Isolate the MCMF solver as an embedded C function that accepts a fixed cost matrix and returns the selected interceptor assignments.
  • Run that function on the Crazyflie main MCU rather than on a workstation MATLAB environment.
  • Measure runtime using a DWT cycle counter or a hardware timer.
  • Benchmark at least two cases: the natural simulation event matrix and a worst-case matrix using the largest candidate and target counts considered in the report.
  • Record compute-only runtime separately from the communication-aware end-to-end budget.
  • Treat retries and medium access delay as part of the communication budget rather than hiding them inside computation time.

The acceptance criterion should also be separated into two levels. First, the report should state whether the solver itself can finish within the available compute budget on the target processor. Second, it should state whether compute time plus a conservative communication budget fits inside the reaction window. No real-time deployment claim should be made unless both conditions are satisfied.

Crazyflie peer-to-peer communication also has practical limitations. Bitcraze's P2P API documentation states that peer-to-peer communication is currently available in broadcast mode and that unicast support is intended for extension [14]. Therefore, a real Crazyflie-based decentralized implementation would require additional protocol design for addressing, acknowledgment, timeout handling, and conflict resolution.

6. Conclusion

This report presents an MCMF-based interceptor assignment method for cooperative multi-target tracking in a mobile WSN. The proposed method changes the assignment objective from legacy minmax fairness to joint assignment efficiency by first maximizing the number of requested interceptor positions filled and then minimizing total assignment cost.

The natural simulation event at t = 39.50 s shows why this objective matters. Using the same calling targets, candidate sensors, and bid-cost matrix, MCMF and legacy minmax can produce different assignments because they optimize different objectives. In the reported event, MCMF reduces total assignment cost while preserving the same worst-team cost.

The report also gives a direct answer to the decentralization question. The current design is leader-coordinated and event-local: one event leader temporarily aggregates bids, a backup leader is defined for failure handling, and the communication burden must be included in the timing budget. Therefore, the current design is not fully decentralized in the strict no-bid-storage sense required by the professor. Finally, Crazyflie-class execution appears plausible for event-triggered use, but it is not yet proven under a full communication-aware real-time budget.
