MCMF-Based Interceptor Assignment for Cooperative Multi-Target Tracking in a Mobile WSN

Yeqi Sang
MIE8888 Final Report Draft

Abstract

This report studies interceptor assignment in a mobile wireless sensor network (WSN) used for cooperative multi-target tracking. In the original simulation, conflict resolution was based on a legacy minimax objective that attempts to minimize the worst team cost among the requesting targets. This objective protects the weakest target assignment, but it does not directly optimize the total resource burden imposed on the sensor network. The proposed Version 46 (V46) assignment module reformulates the problem as a min-cost max-flow (MCMF) problem. Its objective is lexicographic: first maximize the number of filled interceptor slots, then minimize the total assignment cost among solutions with the same number of assigned slots.

The report compares MCMF and the legacy minimax method using the same simulation candidates and the same cost matrices. A real simulation event at t = 39.50 s is used as the primary worked example. The results show that MCMF assigns all requested slots and reduces the total assignment cost from 1.182 to 1.085 in this event. The report also discusses limitations: total-cost minimization does not explicitly protect the worst target team, MATLAB workstation timing is only a prototype baseline, embedded deployment must include communication latency, and the current coordination model is temporary leader-based rather than fully decentralized consensus.

1. Introduction

Mobile wireless sensor networks are useful for monitoring moving targets because mobile sensors can adapt their locations as targets move through the sensing field. In this project, the WSN consists of mobile sensor nodes that cooperatively track up to three moving targets. Each target is intended to maintain two active trackers, a primary tracker and a secondary tracker, so that tracking can continue even when one sensor approaches the edge of its detection range.

The central problem addressed in this report is interceptor assignment during proactive handover. When an active tracker predicts that it will lose a target, idle or non-tracking sensors are asked to move toward a predicted interception point before the target is lost. This process becomes difficult when multiple targets request interceptors at the same time, or when a later target attempts to select a sensor that is already executing an interception task for another target. In these cases, independent target-by-target bidding can create conflicts, duplicate assignments, or unnecessary reassignment of sensors.

The original conflict-resolution method used a minimax-style objective. For simultaneous target conflicts, it attempted to select teams so that the worst target team cost was minimized. This is a fairness-oriented objective: no target should receive a very poor team if a more balanced solution is available. In V46, the interceptor assignment problem is instead formulated as a slot-based global assignment problem and solved using min-cost max-flow. The new method first maximizes the number of assigned interceptor slots and then minimizes the total assignment cost. This changes the objective from worst-team fairness to system-level feasibility and efficiency.

The main contributions of this report are:

  • It reformulates interceptor selection as a global slot-based assignment problem between candidate sensors and target interceptor slots.
  • It compares MCMF and legacy minimax assignments using the same candidate sensors and cost matrices.
  • It uses real simulation evidence to show how the two objectives can make different decisions.
  • It analyzes embedded feasibility and communication limitations for Crazyflie-class deployment.
  • It clarifies that the current coordination design is temporary leader-based, not fully decentralized consensus.

2. Literature Review

2.1 Cooperative Tracking in Mobile WSNs

Wireless sensor networks were originally studied as networks of small sensing, computation, and communication devices with limited resources. Akyildiz et al. describe WSNs as systems constrained by energy, processing, and communication capacity, which is directly relevant to this project because interceptor selection consumes sensor motion, communication, and computation resources [1]. Mobile sensor network surveys further emphasize that mobile sensors can support target searching and tracking, but that mobility introduces planning, coordination, and estimation challenges [2].

The multi-target tracking aspect of this project is related to cooperative multi-robot observation. Parker's CMOMMT work frames the problem as maximizing the time during which moving targets are observed by a team of robots with limited sensing range [3]. Kolling and Carpin also study cooperative observation of multiple moving targets using distributed coordination, prediction of target loss, and local assignment mechanisms [4]. These works motivate the use of mobile sensors and cooperative handover. However, this project focuses more narrowly on the assignment step that occurs when multiple targets compete for replacement interceptors.

2.2 EKF-Based Tracking and Prediction

The simulation uses an Extended Kalman Filter (EKF) to estimate each target state as [x, y, vx, vy]. EKF-based methods are widely used when tracking moving targets with noisy measurements and nonlinear observation models. Bar-Shalom, Li, and Kirubarajan provide a standard tracking and navigation reference for state estimation under uncertainty [5]. More recent WSN tracking work continues to use EKF variants to improve localization and tracking accuracy in sensor networks [6].

In this project, EKF estimates are not the final contribution by themselves. Instead, they provide the prediction inputs for handover: estimated target position, velocity, predicted loss time, and predicted interception point. This makes the assignment problem dependent on estimation quality. A sensor is not only bidding based on geometric distance; it is bidding on an intercept point whose reliability depends on tracking convergence and prediction stability.

2.3 Auction and Bidding-Based Task Allocation

Multi-robot task allocation (MRTA) provides the assignment framework for this project. Gerkey and Mataric show that many multi-robot coordination problems can be analyzed as optimization problems, including assignment and scheduling problems [7]. Market-based or auction-based methods are common because each robot or sensor can express its suitability for a task as a scalar utility or cost. Bertsekas' auction algorithms also connect bidding ideas to assignment and network flow problems [8].

The current simulation already contains a bid cost that combines distance from home, distance to the intercept point, arrival timing, and estimate uncertainty. Therefore, MCMF does not replace the bidding idea. It uses the existing bid as an assignment cost and changes how competing bids are resolved when several targets need interceptors at the same time.

2.4 Minimax and Min-Cost Assignment Objectives

The legacy minimax method and the proposed MCMF method answer different questions. Minimax asks: which assignment minimizes the worst team cost among targets? This protects the least-favored target team and is appropriate when fairness or worst-target quality is the dominant objective. Min-cost assignment asks: which feasible assignment produces the lowest total cost? In this project, MCMF further adds a first priority: fill as many requested slots as possible before minimizing cost.

Minimum-cost flow is a standard network optimization model for assigning limited resources to demand nodes while respecting capacity constraints. Ahuja, Magnanti, and Orlin present minimum-cost flow as a core network optimization problem with broad applications, including assignment and matching [9]. This makes MCMF suitable for the interceptor problem because each sensor can be assigned at most once, each target has a limited number of required slots, and each sensor-target pairing has a cost.

2.5 Distributed Coordination and Embedded Constraints

A real WSN cannot be evaluated only by optimization quality. It must also consider communication latency, coordinator failure, and embedded processor limitations. Decentralized auction methods, such as the consensus-based auction and bundle algorithms, show one way to resolve assignments without a permanent central controller by combining bidding with local consensus [10]. These methods are relevant because the current simulation still uses an event-local coordinator to collect bids and run the global assignment.

Crazyflie-class hardware provides a useful embedded reference point. The Crazyflie 2.0 uses an STM32F405 main processor at 168 MHz and an nRF51822 radio/power processor at 32 MHz [11]. The STM32F405 includes a single-precision floating point unit, but it is still very different from a workstation CPU running MATLAB [12]. The Crazyflie radio stack also imposes packet-size, polling, retry, and peer-to-peer communication constraints [13], [14]. These constraints mean that a final deployment claim requires C-level timing and communication-aware validation, not only MATLAB runtime measurement.

3. System Model and Problem Formulation

3.1 Simulation Setting

The simulation models a mobile WSN with 25 sensors arranged in a 5 by 5 staggered hexagonal grid. The network tracks up to three moving targets. Each target should maintain two active trackers, corresponding to the primary and secondary tracking roles. Sensor-level finite state machine states include IDLE, DETECTING, TRACKING, INTERCEPTING, SEARCHING, and RETURNING_HOME. The handover pipeline for each target progresses through NONE, PENDING_BROADCAST, PENDING_BIDDING, PENDING_SELECTION, and back to NONE.

Table 1. Key simulation parameters.
Parameter Value Description
Number of sensors 25 5 by 5 mobile WSN grid
Number of targets 3 Maximum number of simultaneously tracked targets
Trackers per target 2 Primary and secondary tracker roles
Sensor detection radius 1.5 units Sensor coverage radius
Sensor velocity 0.75 units/s Mobile sensor movement speed
Time step 0.1 s Simulation update interval
Interceptors per calling target 2 Number of replacement interceptor slots requested by each calling target

3.2 Assignment Variables

When one or more targets enter PENDING_SELECTION, the simulation defines a set of calling targets and a set of candidate sensors. Candidate sensors exclude active trackers and sensors that should not be reassigned. For each calling target, the simulation computes a predicted intercept point. For each candidate sensor and each calling target, the simulation computes one bid cost. These bid values form the assignment cost matrix:

B[i, j] = bid cost of assigning candidate sensor i to calling target j

Each calling target requires two interceptor slots. A target slot is one required interceptor position for that target. For example, if targets 1 and 2 are calling, and each target requires two interceptors, the assignment problem has four target slots: target 1 slot A, target 1 slot B, target 2 slot A, and target 2 slot B.

3.3 Bid Cost Function

The bid cost represents how suitable a sensor is for a target. A lower bid indicates a better candidate. The simulation uses a weighted cost:

bid = w1 * P_home + w2 * P_spatial + w3 * P_temporal + w4 * P_uncertainty

The four terms have system meaning:

  • P_home penalizes displacement from the sensor's home grid position.
  • P_spatial penalizes distance from the sensor to the target intercept point.
  • P_temporal penalizes poor arrival timing relative to the target motion and loss deadline.
  • P_uncertainty penalizes low confidence in the shared target estimate.

Therefore, total bid cost is not an arbitrary number. It is an approximation of network-wide resource burden, including sensor displacement, intercept feasibility, timing quality, and estimation reliability.

3.4 Problem Statement

The interceptor assignment problem can be stated as follows. Given a set of calling targets, a set of candidate sensors, and a sensor-target cost matrix, assign candidate sensors to target interceptor slots such that:

  • Each target requests two interceptor slots.
  • Each candidate sensor can be assigned at most once.
  • Active trackers are excluded from the candidate set.
  • The assignment should fill as many requested slots as possible.
  • Among assignments with the same number of filled slots, the assignment should minimize total bid cost.

Conflicts occur when multiple targets compete for overlapping low-cost candidates, or when a later target attempts to select a sensor that is already assigned as an interceptor for another target.

4. Proposed MCMF-Based Assignment Method

4.1 Assignment Graph

The MCMF solver expands each calling target into two interceptor slots and builds a directed flow graph:

  • The source connects to each candidate sensor node with capacity 1 and cost 0.
  • Each candidate sensor connects to each target slot with capacity 1 and cost equal to the corresponding bid value.
  • Each target slot connects to the sink with capacity 1 and cost 0.

The capacity from the source to each sensor enforces the rule that one sensor cannot be assigned to more than one target slot. The target-slot-to-sink capacity enforces the number of requested interceptors per target. The cost on each sensor-to-slot edge encodes the bid cost for assigning that sensor to that target.

4.2 Lexicographic Objective

The solver objective is lexicographic. The first objective is to maximize the number of assigned slots. The second objective is to minimize the total assignment cost among solutions with the same number of assigned slots. In implementation, a large assignment reward is subtracted from each feasible sensor-to-slot edge cost. This makes each additional filled slot more valuable than any possible cost reduction from leaving a slot empty.

Objective 1: maximize assigned interceptor slots
Objective 2: minimize total assignment cost, conditional on Objective 1

4.3 Why This Objective Fits the System

The main system requirement is to sustain target tracking by replacing trackers before they lose contact. Therefore, filling interceptor slots is a feasibility objective. If a target does not receive enough replacement sensors, then the system may lose tracking continuity regardless of how fair the remaining assignment appears. This is why the proposed method first maximizes the number of assigned slots.

After slot filling is handled, total cost becomes the correct secondary objective for this system because the bid cost already represents network-wide resource burden. A solution with lower total bid cost tends to use sensors that are closer to home, closer to the intercept point, better timed, and supported by more reliable estimates. Over repeated handovers, reducing this total burden helps preserve future network availability.

The legacy minimax objective remains meaningful. It protects the worst target team and is appropriate when worst-target fairness is the dominant mission goal. However, minimax may accept higher total resource expenditure to balance team costs. In a resource-constrained mobile WSN, it is not always desirable to sacrifice total network efficiency only to improve the worst single team cost, especially when the dual-tracker requirement and handover gates already provide target-level protection before assignment.

4.4 Limitation of the Objective

The proposed MCMF objective does not explicitly minimize the worst target team cost. Therefore, it does not provide the same fairness guarantee as minimax. If a mission requires strict worst-target protection, the assignment formulation should be extended with a maximum per-target team cost constraint or with a secondary fairness term. In this report, minimax is treated as a valid fairness baseline, not as an incorrect method.

5. Experimental Design

The validation is organized in stages so that algorithm correctness, simulation integration, and system behavior can be evaluated separately. This is important because a full simulation run can hide whether an observed behavior comes from the assignment solver, the EKF timing, target motion, or animation state.

Table 2. Validation stages.
Stage Purpose Evidence What it does not prove
Stage 1 Verify solver correctness on mock cost matrices. Unit tests check feasible assignment, non-duplicate sensors, shortage behavior, and total-cost calculation. Does not prove compatibility with full simulation state.
Stage 2 Verify adapter compatibility with simulation-shaped data. Tests build candidate lists and cost matrices using simulation-like sensor positions, active trackers, and intercept points. Does not prove natural event timing.
Stage 3 Compare MCMF and minimax under controlled conflict injection. Two targets are forced into simultaneous PENDING_SELECTION so both algorithms can be compared on the same input. Does not prove the conflict occurs naturally.
Stage 4 Analyze natural or reselection conflict behavior in a full simulation run. Real log event at t = 39.50 s shows joint reselection and A/B assignment comparison. Does not prove embedded real-time deployment.

For fair comparison, both MCMF and the legacy minimax solver use the same calling targets, candidate sensors, and cost matrix. The only changed element is the assignment objective.

6. Results and Comparative Analysis

6.1 Real Simulation Conflict Event at t = 39.50 s

The main real-run evidence comes from a full V46 simulation log. At t = 38.90 s, target 1 had already selected sensors 10 and 14 as interceptors. At t = 39.50 s, target 2 entered PENDING_SELECTION. A provisional selection for target 2 attempted to use sensor 14, but sensor 14 was already assigned as an interceptor for target 1. Therefore, target 1 was added to a joint reselection group, its intercept point was refreshed using tracker 9, and the system solved a shared assignment problem for targets 2 and 1.

6.2 Worked Example: Why the Methods Differ

Step 1: Conflict trigger.

Target 2 entered PENDING_SELECTION and sensor 14 appeared as its best candidate. However, sensor 14 was already assigned to target 1. Allowing target 2 to take sensor 14 would disrupt target 1's existing interception task. Therefore, the system grouped target 2 and target 1 into a joint reselection problem.

Step 2: Legacy minimax decision.

The legacy method evaluates non-overlapping two-sensor teams and selects the combination that minimizes the maximum team cost across targets. In this event, it assigns target 2 to sensors 20 and 13 with team cost 0.591, and target 1 to sensors 14 and 18 with team cost 0.590. The result is very balanced because the two team costs are almost equal.

Step 3: MCMF decision.

MCMF first fills all four requested interceptor slots. Then it minimizes total cost. It assigns target 2 to sensors 13 and 20 with team cost 0.591, and target 1 to sensors 10 and 14 with team cost 0.493. This produces a total cost of 1.085, compared with 1.182 for legacy minimax.

Step 4: System interpretation.

The legacy solution is fairness-oriented: it gives both targets nearly equal team costs. The MCMF solution is system-efficiency-oriented: it keeps all requested slots filled and reduces the total network burden. In this event, MCMF does not worsen the worst team cost, but it does avoid an unnecessarily expensive assignment for target 1. This supports the argument that total-cost minimization is useful when the system objective is to preserve global WSN resources across repeated handovers.

7. Discussion

7.1 Why Total Cost After Slot Maximization Is Used

The strongest argument for the proposed objective is that it matches the mission hierarchy of the simulation. The first requirement is not fairness; it is maintaining tracking feasibility by filling interceptor slots. If the system cannot assign replacement sensors, the target may be lost. Therefore, the first optimization layer is to maximize assigned slots.

Once slot coverage is handled, total cost is the most appropriate secondary objective because the cost function represents system burden. A lower total assignment cost means that, across all targets, the selected sensors are collectively better positioned, less displaced from home, better timed, or supported by more reliable estimates. This is especially important in a repeated handover system because a locally fair but globally expensive assignment can reduce future availability.

This does not mean minimax is wrong. Minimax is the better objective if the mission requires strict worst-target fairness. The proposed method simply chooses a different priority: do not sacrifice network-wide feasibility and efficiency unless fairness is explicitly required by the mission specification.

7.2 Embedded Runtime and Communication Budget

The measured MATLAB runtime should be treated as an optimistic prototype baseline. A laptop CPU running MATLAB has a different architecture from a small embedded processor. It has different cache behavior, memory bandwidth, instruction scheduling, and floating point support. A deployed implementation would run in C or C-like firmware, not MATLAB. It may use single-precision floating point, fixed point, or soft-float arithmetic depending on the target platform.

The 0.1 s time step also cannot be assigned entirely to computation. The coordinator must broadcast the handover request, receive bids from candidate sensors, run assignment, broadcast the result, and possibly receive acknowledgments. A simple event-level communication model is:

N_packets = 1 request + M bid messages + 1 result + K * N acknowledgments

For the real t = 39.50 s event, M = 23 candidate sensors, N = 2 calling targets, and K = 2 requested interceptors per target. This gives:

N_packets = 1 + 23 + 1 + 2 * 2 = 29 packets

If the system assumes an optimistic 2 ms per reliable packet transaction, based on Bitcraze's low-latency Crazyradio discussion for 2 Mbps communication without retries, then 29 sequential packet transactions would require approximately 58 ms before collision, retry, scheduling, and control overhead are included [13]. Therefore, the realistic deadline is an end-to-end budget:

T_total = T_request + T_bid_collection + T_compute + T_result + T_ack + T_retry

This means the algorithm should be described as event-triggered and plausible, not proven real-time on embedded hardware. The MCMF solver does not need to run at every timestamp. It runs when a target reaches PENDING_SELECTION or when joint reselection is triggered.

7.3 Crazyflie-Class Feasibility

Crazyflie 2.0 is a useful lower-end reference platform for this project. Its main application processor is an STM32F405, an Arm Cortex-M4 processor at 168 MHz with 192 KB SRAM and 1 MB flash [11]. ST's documentation states that the STM32F405 family includes a single-precision floating point unit and DSP instructions [12]. Therefore, Crazyflie 2.0 is not a no-FPU platform, but it is still much less capable than a 4.5 GHz workstation CPU.

Using the measured MCMF-only workstation time of 0.001254 s and a simple frequency-scaling estimate from 4.5 GHz to 168 MHz gives:

estimated_cycles = 0.001254 * 4.5e9 = 5.64e6 cycles
estimated_time_at_168MHz = 5.64e6 / 168e6 = 0.0336 s

This is approximately 33.6% of a 0.1 s time step for computation alone. Because this estimate ignores communication, firmware scheduling, sensor processing, and flight control load, it should be treated as a warning rather than a guarantee. The result suggests that Crazyflie-class execution may be possible for event-triggered assignment, but a hard 0.1 s end-to-end guarantee has not been proven.

7.4 Decentralization Limitation

The current simulation should be described as temporary leader-based coordination, not fully decentralized consensus. A practical event protocol could be:

  • For a single-target handover, the current primary tracker of that target acts as the temporary coordinator.
  • For a joint conflict, the primary tracker of the target with the earliest predicted loss time acts as the coordinator.
  • If there is a tie, the lower target ID and then the lower sensor ID are used as tie-breakers.
  • If the coordinator fails or times out, the secondary tracker takes over.
  • If the secondary tracker also fails, the system falls back to local greedy assignment or keeps existing interceptors until the next event window.

This protocol removes a permanent central controller, but it still requires one temporary event leader to collect or reconstruct the bid matrix during the assignment event. Therefore, it does not satisfy a strict no-bid-storage decentralized requirement. A stricter future version would use a distributed auction or consensus-based assignment method, where sensors exchange local winning bids and no single node stores the full bid matrix.

Crazyflie peer-to-peer communication also has practical limitations. Bitcraze's P2P API documentation states that peer-to-peer communication is currently available in broadcast mode and that unicast support is intended for extension [14]. Therefore, a real Crazyflie-based decentralized implementation would require additional protocol design for addressing, acknowledgment, timeout handling, and conflict resolution.

8. Conclusion

This report presented an MCMF-based interceptor assignment method for cooperative multi-target tracking in a mobile WSN. The proposed method changes the assignment objective from legacy minimax fairness to slot-aware system efficiency. It first maximizes the number of assigned interceptor slots and then minimizes total assignment cost.

The real simulation event at t = 39.50 s shows why this objective matters. Both legacy minimax and MCMF filled all four requested slots, but MCMF reduced total assignment cost from 1.182 to 1.085. In this event, MCMF also preserved the same worst-team cost while reducing network-wide resource burden. This supports the use of MCMF when the system objective is to preserve global WSN efficiency across repeated handovers.

The method is not yet proven for embedded deployment. MATLAB workstation timing is only a baseline. A Crazyflie-class 168 MHz processor may be computationally plausible for event-triggered MCMF execution, but the complete 0.1 s deadline must include communication latency, retries, firmware scheduling, and flight-control load. The current coordination model is also temporary leader-based rather than fully decentralized. Future work should implement the assignment module in embedded C, measure processor-in-the-loop runtime, add communication-in-the-loop tests, and investigate a stricter distributed auction or consensus protocol.
